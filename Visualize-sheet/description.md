# sheetVis 设计与维护说明

## 首版范围

面向当前 Linux 电脑的本地 Web 工具，暂只播放钢琴。首要输入是清晰排版 PDF 和扫描 PDF；识别后直接进入播放，不强制人工确认。MusicXML 和 MIDI 可以绕过识别。示例为自写的八小节 C 大调练习。

左右手用绿色与蓝色区分。88 键瀑布、键盘亮键、五线谱小节光标、声音和位置控制共享时间线。支持 0.25–2 倍速、20–300 BPM 参考速度输入、暂停、前后 5 秒、进度条、小节定位、分手静音、音量、4／7／12 秒预览和识别结果下载。页面在较窄屏幕中保留可横向浏览的钢琴键盘；首版没有手机服务或桌面安装包。

## 架构与文件

- `server.py`：标准库 HTTP 服务，监听 loopback，提供健康查询、异步识别队列、日志和导出结果，服务 `dist/`。
- `src/score.ts`：MusicXML／MXL／MIDI 转播放事件；保留小节、谱表、速度、音符和提示。
- `src/audio.ts`：Web Audio 本地采样播放器。音频时钟决定播放位置，每 25 ms 调度未来约 120 ms 的音符。
- `src/waterfall.ts`：Canvas 音符瀑布、88 键键盘、音符名与小节线。
- `src/main.ts`、`src/style.css`：界面、导入、自动播放、原 PDF 与五线谱切换、位置同步。
- `public/demo.musicxml`：自写示例；`public/samples/`、`public/licenses/`、`public/credits.html`：本地资源与署名。
- `scripts/setup.py`：隔离下载、校验及解包运行时；`scripts/launch.py`、`launch.sh`：本地启动与浏览器打开。
- `tests/`：音乐语义、音频调度、HTTP 边界、真实浏览器与 PDF 全链路测试。

PDF 数据经 `POST /api/recognize` 上传至本机，返回任务 ID。前端轮询状态；后端先到 GRID 筛选页面，再启动 Audiveris 导出，生成 MusicXML 后前端解析并自动播放。多个导出文件作为不同乐章呈现。原始 PDF、输出、日志和输入 SHA256 保存在 `.data/jobs/<id>/`。重启后恢复磁盘任务记录，原来正在等待／执行的任务标记为中断；重新导入相同 PDF 可以继续其保存的 OMR 阶段。

MusicXML 事件以四分音符为一个 beat；`backup`／`forward` 处理多声部对齐，和弦共享起点。实际 `duration / divisions` 决定时长，适用于附点与连音。连续的延音线合并为一次发声。普通反复和常见不同结尾展开成播放顺序，速度变化经分段积分转换成秒。踏板延长声音，而瀑布音符长度保留按键时值。谱表 1 视为右手，谱表 2 及以上视为左手，这是分手显示规则，不能准确表达所有跨谱表的手分配。

MusicXML 多乐器输入选择标为钢琴的声部，否则选择第一声部并提示。MIDI 优先选择钢琴音色轨，滤除打击乐；左右手按音轨平均音域或单轨音高估计。MIDI 的变速、声音与视觉基于解析后的秒时间线。

调速改变时间线速率，不改变音高。手动 BPM 按相对初始速度的比例缩放整条时间线，保留各段速度的相对变化；倍速再基于此参考速度调整。时长显示、瀑布秒刻度和五秒跳转随参考速度统一换算。暂停、跳转、调速和分手切换清理既有声音；恢复时重建目标位置仍持续的音符，使用对应采样偏移。播放启动和异步载入有版本保护，防止旧乐谱、旧识别任务或旧音色载入结果覆盖新操作。很长的持续音受采样原长度限制，声音最终可能自然衰减。

## 本地运行边界

正常使用时，前端、钢琴音色、识别运行时和英文 OCR 模型均为本地资源，不依赖 CDN，不上传到外部服务。首次 `npm ci`／`npm run setup` 需要联网下载公共依赖。开源来源页面包含用户可主动打开的外部链接。

HTTP 服务检查 Host，写请求检查 Origin 和专用请求头；阻止静态路径越界，返回 no-store 响应。最大输入 40 MB，队列最多八个等待／运行任务；默认单任务预算为 3600 秒，可在配置中设为 30–7200 秒，排队不消耗识别预算。停止服务会取消等待任务，并结束服务创建的识别进程组。识别不是沙盒执行，适合本机个人使用；没有开放局域网、账户、多用户权限或公开部署。Audiveris 的 XDG 配置、缓存、数据、Java home/preferences 都指向 `.data/engine/`，不修改原有用户配置。

## 限制与下一步

PDF 自动识别不能保证正确。首版通过明确提示、原 PDF 对照、日志和 MusicXML 导出来处理异常，没有内建音符编辑器或可信的逐音符置信度。不支持手写谱保证，也没有真实钢琴谱集的准确率基准。

目前支持 `score-partwise`；`score-timewise` 需先转换。装饰音、颤音等按已标明的主音播放或跳过，并给提示；D.C.／D.S.／Coda 不展开。复杂嵌套反复、所有跨谱表手分配、八度线和移调、细致力度／奏法解释、渐变速度、半踏板等尚未完整实现。五线谱光标定位到当前小节，不逐音符移动。MIDI 无五线谱渲染。音色是单层采样近似，速度改变后已持续音的恢复不是完整声学重建。

需要继续以用户真实 PDF 评估错音、漏音、节奏、分手和反复结构，逐项记录输入出处、预期时间线与实际识别结果；针对常见错误再决定是否加入音符纠错、其他 OMR 引擎或更完整的 MusicXML 解释。

## 开发与验证

```bash
npm test
npm run build
npm run test:browser
npm run test:pdf
```

开发时先运行 `npm start` 启动识别服务，再运行 `npm run dev`；Vite 将 `/api` 代理到本机 4280。生产服务读取 `dist/`，修改前端或本地公共资源后需重新构建。修改服务端后重启 Python 服务。

`tests/pdf.mjs` 默认使用本机 4280 服务，可设置 `SHEETVIS_TEST_URL` 指向其他本地端口。输入是 `tests/fixtures/demo-score.pdf`，来自首版自写示例的 OSMD 打印结果；测试导入、等待识别、自动播放、BPM 和原 PDF 切换。截图和运行记录放在 `test-results/`，不是用户作品或真实谱集准确率基准。Chromium 默认路径为 `/usr/bin/chromium`，可用 `CHROMIUM_PATH` 覆盖。

## 2026-10-14 默认肖邦乐谱、识别反馈与 Zen

当前默认服务使用 `127.0.0.1:4280`。本次启动前确认 4280／4283 都没有监听服务，不占用或中断之前的任务。`config.json` 的 `default_score` 指向用户指定的 `/home/a/Documents/materials/PianoSheets/chopin_ballade1.pdf`；只读原文件，识别副本保存在私有 `.data/jobs/`，不会把该 PDF 放入公开静态资源或上传外部服务。

`GET /api/config` 提供默认文件名和配色，`GET /api/default-score` 只读取配置指定的文件，不接受客户端提供文件路径。前端默认读入 PDF、提交本地识别，并显示文件名、大小、总页数、乐谱页数和状态。首次打开浏览器通常没有音频权限，文件仍正常载入，显示“音频待启用”；点击播放或按空格后启用声音。用户从文件选择或拖放导入时仍可自动播放。

识别任务按输入 SHA256 与处理流程版本复用正在执行或已完成的结果，避免刷新重复排队；缓存文件缺失时重新识别。失败任务的 `.omr` 可作为相同文件下一次任务的输入，新任务保留 `resumed_from` 和 `previous.log`，不覆盖原任务。Audiveris 采用 `-swap`、关闭引擎并行、限制 Java 可见 CPU 为 2，并保留 2 GB 堆上限。分阶段保存减少长谱内存压力；具体策略依据 [Audiveris CLI](https://audiveris.github.io/audiveris/_pages/guides/advanced/cli/) 与 [5.11.0 OmrExecutors 源码](https://github.com/Audiveris/audiveris/blob/5.11.0/app/src/main/java/org/audiveris/omr/util/OmrExecutors.java)。每张选中乐谱页必须达到 PAGE，未完成的部分不能只因生成了 MXL 就报告 100% 成功。

质量反馈使用真实的引擎日志和解析数据，列出音符／分手／小节数量、节奏无法配平的位置与 PDF 页码、和弦起奏位置缺失、小节导出异常、超出钢琴范围和已知播放限制。不把阶段百分比当作准确率；`quality.accuracy` 明确为 `null`。没有引擎警告也只说明结构检查通过，不能证明没有错音或漏音。`src/quality.ts` 生成反馈内容。

实测发现导出 XML 含不同结尾标记，却没有反复记号：此前解析器会跳过第 129 小节之后的内容。现在这类不成立的结尾标记不参与筛选，按谱面顺序播放，并显示检查记录；有效的反复与不同结尾仍按原有语义展开。破损八度线会触发 OSMD 排版异常：正常预览失败时，预览副本省略八度线并明确告知；原 XML、下载文件和播放音高不作此修改。MusicXML 的 octave-shift 是相对音高数据的显示移位，参照 [MusicXML 4.0 octave-shift](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/octave-shift/)。自动重排改由应用受控处理，避免失败渲染的 resize 回调不断抛错。

瀑布左右手、触键与背景颜色可以修改 `config.json.colors`，也可在右侧工具栏“瀑布配色”调整。浏览器设置立即应用，保存为 `sheetvis.colors`，优先于配置文件；“恢复配置配色”清除此覆盖。只接受已有字段与六位十六进制颜色。键盘高度继续独立保存。

## 2026-10-15 八度线、行内谱号、弧线与连音支持

### 实现与播放语义

PDF 符号识别仍由本机 Audiveris 完成。本次补齐识别结果到播放／原谱定位的处理，不把程序生成的数据统计当作原谱准确率。

- 八度线：保留 `octave-shift` 及原始实际音高；8va／8vb 已包含在标准 MusicXML 的 `pitch` 中，不额外升降八度。新增按谱表和编号检查起止配对，缺失、重复或孤立端点进入反馈，不猜测延伸范围。重建预览先尝试保留八度线，确实遇到排版异常才回退并提示；原始下载保持完整。参见 [MusicXML octave-shift](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/octave-shift/)。
- 行内谱号：原 PDF 定位按发生拍点应用谱号，处理 backup 后的其他声部，而不把小节末的谱号提前套到开头；涵盖谱号所在谱线和 `clef-octave-change`。音高仍按 MusicXML 明确写出的音高播放，手别由谱表保留。小节中途 `divisions` 变化也按顺序解析。定位映射缓存由 v3 升至 v4，仅重新计算坐标，不重新识别整份 PDF。
- 延音线：`tie`／`tied` 的 start、stop、continue 支持跨小节续接；同音高、同声部且时间连续时合并为一次击键，保留每个原始符头的高亮区间。跨谱表续接只接受唯一候选，避免误合并同时出现的同音。缺少起始音时独立播放并提示。
- 连奏线：按编号配对，可跨小节；保留每个音的起奏及谱面时值，仅在同声部、连续且同属一条连奏线的音之间增加至多 30ms、且不超过下音时长 10% 的声音衔接。同音重击不延迟，休止不跨越，其他声部不因位于弧线的时间范围内而被改变。缺失终点的线不推测作用范围。这是当前的采样播放诠释，不是专业演奏建模。
- 连音：显式 `duration / divisions` 优先，三／五／六连音等不重复缩放。缺少 duration 时才依据音符类型、附点和 `normal-notes / actual-notes` 恢复，并提示人工检查；非法比例不生成猜测音符。参见 [MusicXML time-modification](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/time-modification/) 和 [duration](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/duration/)。
- “反馈”显示 MusicXML 的八度线起点、谱号变更、连奏线起点、合并延音数量，以及连音音符数；三／五连音统计是参与的音符数，不是连音组数。

## 2026-10-15 倚音与装饰音

新增 `src/ornaments.ts`，在延音线、踏板及连奏线解析之后，将 MusicXML 中已识别的装饰奏法展开为实际播放事件。原 XML 不改写，下载与五线谱保持原始记号。PDF 图像分类仍由 Audiveris 完成；本次不包含新图像模型训练，不能据此宣称扫描 PDF 的漏识别率下降。

## 2026-10-15 本地多线程识别

原实现给 Audiveris 强制传入 `OmrExecutors.useParallelism=false`，并固定 Java `ActiveProcessorCount=2`。现启用 Audiveris 页内处理的线程池，以并行处理系统级识别阶段；CPU 预算由配置决定。Python 任务队列仍为一份乐谱接一份乐谱，保留原有取消、超时和断点续识别机制，避免多份大型 PDF 争抢内存。

### 配置与资源边界

- `recognition_threads`：整数 0–16。默认 0 自动选择不超过 4 且尽可能保留一个可用核心；1 关闭内部并行；2–16 指定 CPU 预算，并限制到进程可用 CPU 数。它不是 JVM 所有线程数量的硬上限，识别引擎和 JVM 还有管理线程。
- `recognition_memory_mb`：整数 512–8192，默认 2048，作为 Java 堆上限；不代表整个进程的总内存上限。自动模式根据 Linux MemAvailable 降低并发和堆预算，显式指定并发时应自行匹配内存。
- `OMP_THREAD_LIMIT=1`、`OMP_NUM_THREADS=1` 避免每个识别工作线程再启动大量原生 OCR 线程。
- 显式保留 `Book.processAllStubsInParallel=false`，按页顺序处理；上游跨页并发使用可增长线程池，简单打开它不能用 ActiveProcessorCount 保证同时驻留的页数，长 PDF 有显著内存压力。因此本次优先采用有 CPU 预算的页内并行，不把每一页都同时载入。
- 本地日志和任务 API 的 `resources` 记录实际选择的资源，“反馈”显示 CPU 预算及 Java 堆上限。运行中的识别不热切换，配置在新任务开始时读取；相同 PDF 的完成缓存继续复用，不为切换线程数强制重跑。

实现依据为固定版本 [Audiveris 5.11.0 OmrExecutors](https://github.com/Audiveris/audiveris/blob/5.11.0/app/src/main/java/org/audiveris/omr/util/OmrExecutors.java) 和 [Book.reachBookStep](https://github.com/Audiveris/audiveris/blob/5.11.0/app/src/main/java/org/audiveris/omr/sheet/Book.java)。仍完全本地运行，不增加联网调用。

### 性能与结果验证

用 `python scripts/benchmark_threads.py` 对已有 `tests/fixtures/demo-score.pdf` 做两次独立冷识别，临时任务目录不接触生产 `.data/jobs`，各运行都执行 GRID → PAGE → 导出，不使用识别结果缓存。单核 56.095 秒、四核 32.036 秒，约 1.75 倍速度、耗时减少 43%。两次输出均为 56 个有音高的音符，按乐章／小节比较音符音高、时值、声部、谱表、和弦／休止及 backup／forward 的顺序完全一致，引擎节奏异常、缺失起奏位置和导出异常均为零。

记录在 `test-results/thread-benchmark/result.json` 及同目录单核／四核日志。只有一轮短谱对照，文件系统缓存、JVM 启动和系统负载影响耗时；这不是长谱、多页扫描或识别准确率的证明。可运行 `python scripts/benchmark_threads.py /路径/乐谱.pdf --threads 4` 对指定文件复测，耗时取决于输入；脚本保留统计和日志，临时识别文件结束后删除。

## 2026-10-15 中断识别与默认缓存

### 中断和续识别

识别进度条与缓存列表提供“中断识别”，本机请求通过 `POST /api/jobs/<id>/cancel` 提交。排队任务从 executor Future 中取消并记为 cancelled；运行任务先进入 cancelling，只终止属于该任务的 Audiveris 进程组，工作线程退出后才持久化为 cancelled。取消指定排队任务不会误停另一个活动任务。重复取消已结束任务保持终态，不误报为新的中断。取消终态不再等待到超时，也不会被迟到的 done 更新覆盖；cancelling 期间继续禁止删除缓存。

保留上传副本、日志和有效进度。PAGE 前及完成后原子保存备用 `checkpoint.omr`；中断发生在工作工程写入期间时，后续可回退到备用工程。“继续识别”读取原上传副本并提交新记录，优先复用有效工作工程，损坏时尝试备用检查点；没有可用检查点则从原 PDF 重算，未保存的阶段不承诺恢复。续识别使用流式 ZIP 复制，重定位 book 输入路径到新记录的 PDF，避免原中断缓存删除后新任务仍依赖旧路径，也避免整份工程先解压进 Python 内存。早期 GRID 未完成的中断可能需要重新筛选页面。

Python 的短处理／检查点复制阶段会在安全边界检查中断；它们运行期间界面可能暂显示“正在中断”。Java 进程先请求终止，最多等待 5 秒后强制结束。原始电脑文件不修改，不把未完成导出当作可播放的完成缓存。

### 默认乐谱缓存

已完成且 PDF 与导出结果齐全的记录可以“设为默认”，经 `POST /api/cache/<id>/default` 原子保存为 `config.json` 的 `default_cache`，保留原 `default_score`、颜色和资源设置。缓存列表标出当前有效默认项。启动／“默认乐谱”通过配置返回的 job_id 直接读取该记录，不再提交识别；已有缓存不会因流程版本或资源配置变化被默认打开操作强制重跑。

删除默认缓存时先清除默认指向，恢复原 default_score；记录或文件缺失时也回退到原文件，没有默认文件则打开示例。明确设置的 `SHEETVIS_DEFAULT_SCORE` 环境变量保留最高优先级。未完成、中断或结果缺失的记录不可设为默认。默认缓存选择只改变以后打开的默认项，不立即替换当前正在播放的曲目。
