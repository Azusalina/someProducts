# sheetVis 设计与维护说明

## 首版范围

面向当前 Linux 电脑的本地 Web 工具，暂只播放钢琴。首要输入是清晰排版 PDF 和扫描 PDF；识别后直接进入播放，不强制人工确认。MusicXML 和 MIDI 可以绕过识别。示例为自写的八小节 C 大调练习。

左右手用绿色与蓝色区分。88 键瀑布、键盘亮键、五线谱小节光标、声音和位置控制共享时间线。支持 0.25–2 倍速、20–300 BPM 参考速度输入、暂停、前后 5 秒、进度条、小节定位、分手静音、音量、4／7／12 秒预览和识别结果下载。页面在较窄屏幕中保留可横向浏览的钢琴键盘；首版没有手机服务或桌面安装包。

钢琴采样由 Nicholaus P. Brosowsky 编辑，原来源表将钢琴标为 VSO2 / Versilian Studios。本工具没有引入其加载器代码；采样原文件未修改，播放时作邻近采样变调与包络处理。完整署名、来源和许可说明提供于 `public/credits.html`、`public/licenses/` 和 `public/samples/`，构建后也可从页面页脚访问。

Audiveris 固定为 5.11.0 Ubuntu 24.04 x86_64 包，在项目目录解包，不运行系统安装脚本。其公开发行包 SHA256 为 `f20113aaa33b3149ec8d6a09b2a7963360e65fafd92d69389987a85bbc3ec7a3`。下载脚本验证此值，并保存 `.runtime/provenance.json`。采样与 OCR 模型在初次准备时锁定上游提交，文件校验和保存在各自 manifest 中；后续准备复用所记录提交。第三方组件保留原许可证与随包版权文件。

## 架构与文件

- `server.py`：标准库 HTTP 服务，监听 loopback，提供健康查询、异步识别队列、日志和导出结果，服务 `dist/`。
- `src/score.ts`：MusicXML／MXL／MIDI 转播放事件；保留小节、谱表、速度、音符和提示。
- `src/audio.ts`：Web Audio 本地采样播放器。音频时钟决定播放位置，每 25 ms 调度未来约 120 ms 的音符。
- `src/waterfall.ts`：Canvas 音符瀑布、88 键键盘、音符名与小节线。
- `src/main.ts`、`src/style.css`：界面、导入、自动播放、原 PDF 与五线谱切换、位置同步。
- `public/demo.musicxml`：自写示例；`public/samples/`、`public/licenses/`、`public/credits.html`：本地资源与署名。
- `scripts/setup.py`：隔离下载、校验及解包运行时；`scripts/launch.py`、`launch.sh`：本地启动与浏览器打开。
- `tests/`：音乐语义、音频调度、HTTP 边界、真实浏览器与 PDF 全链路测试。

PDF 数据经 `POST /api/recognize` 上传至本机，返回任务 ID。前端轮询状态；后端串行启动 `Audiveris -batch -export -save`，生成 MusicXML 后前端解析并自动播放。多个导出文件作为不同乐章呈现。原始 PDF、输出、日志和输入 SHA256 保存在 `.data/jobs/<id>/`。重启后内存任务列表会清空，磁盘记录仍保留。

MusicXML 事件以四分音符为一个 beat；`backup`／`forward` 处理多声部对齐，和弦共享起点。实际 `duration / divisions` 决定时长，适用于附点与连音。连续的延音线合并为一次发声。普通反复和常见不同结尾展开成播放顺序，速度变化经分段积分转换成秒。踏板延长声音，而瀑布音符长度保留按键时值。谱表 1 视为右手，谱表 2 及以上视为左手，这是分手显示规则，不能准确表达所有跨谱表的手分配。

MusicXML 多乐器输入选择标为钢琴的声部，否则选择第一声部并提示。MIDI 优先选择钢琴音色轨，滤除打击乐；左右手按音轨平均音域或单轨音高估计。MIDI 的变速、声音与视觉基于解析后的秒时间线。

调速改变时间线速率，不改变音高。手动 BPM 按相对初始速度的比例缩放整条时间线，保留各段速度的相对变化；倍速再基于此参考速度调整。时长显示、瀑布秒刻度和五秒跳转随参考速度统一换算。暂停、跳转、调速和分手切换清理既有声音；恢复时重建目标位置仍持续的音符，使用对应采样偏移。播放启动和异步载入有版本保护，防止旧乐谱、旧识别任务或旧音色载入结果覆盖新操作。很长的持续音受采样原长度限制，声音最终可能自然衰减。

## 本地运行边界

正常使用时，前端、钢琴音色、识别运行时和英文 OCR 模型均为本地资源，不依赖 CDN，不上传到外部服务。首次 `npm ci`／`npm run setup` 需要联网下载公共依赖。开源来源页面包含用户可主动打开的外部链接。

HTTP 服务检查 Host，写请求检查 Origin 和专用请求头；阻止静态路径越界，返回 no-store 响应。最大输入 40 MB，队列最多八个等待／运行任务，单任务十分钟超时。停止服务会取消等待任务，并结束服务创建的识别进程组。识别不是沙盒执行，适合本机个人使用；没有开放局域网、账户、多用户权限或公开部署。Audiveris 的 XDG 配置、缓存、数据、Java home/preferences 都指向 `.data/engine/`，不修改原有用户配置。

## 限制与下一步

PDF 自动识别不能保证正确。首版通过明确提示、原 PDF 对照、日志和 MusicXML 导出来处理异常，没有内建音符编辑器或可信的逐音符置信度。不支持手写谱保证，也没有真实钢琴谱集的准确率基准。

目前支持 `score-partwise`；`score-timewise` 需先转换。装饰音、颤音等按已标明的主音播放或跳过，并给提示；D.C.／D.S.／Coda 不展开。复杂嵌套反复、所有跨谱表手分配、八度线和移调、细致力度／奏法解释、渐变速度、半踏板等尚未完整实现。五线谱光标定位到当前小节，不逐音符移动。MIDI 无五线谱渲染。音色是单层采样近似，速度改变后已持续音的恢复不是完整声学重建。

需要继续以用户真实 PDF 评估错音、漏音、节奏、分手和反复结构，逐项记录输入出处、预期时间线与实际识别结果；针对常见错误再决定是否加入音符纠错、其他 OMR 引擎或更完整的 MusicXML 解释。

## 开发与验证

```bash
npm test
npm run build
npm run test:browser
npm run test:pdf
```

开发时先运行 `npm start` 启动识别服务，再运行 `npm run dev`；Vite 将 `/api` 代理到本机 4280。生产服务读取 `dist/`，修改前端或本地公共资源后需重新构建。修改服务端后重启 Python 服务。

`tests/pdf.mjs` 默认使用本机 4280 服务，可设置 `SHEETVIS_TEST_URL` 指向其他本地端口。输入是 `tests/fixtures/demo-score.pdf`，来自首版自写示例的 OSMD 打印结果；测试导入、等待识别、自动播放、BPM 和原 PDF 切换。截图和运行记录放在 `test-results/`，不是用户作品或真实谱集准确率基准。Chromium 默认路径为 `/usr/bin/chromium`，可用 `CHROMIUM_PATH` 覆盖。

2026-10-14 首轮验证结果：

- `npm test`：22 项音乐语义与音频调度测试、11 项本地服务测试全部通过。包括双谱表／和弦对齐、休止、连音时值、速度变化、延音线、反复、不同结尾、踏板、弱起、未满小节、MXL、MIDI、暂停／跳转长音恢复、变速音高保持、异步播放取消、Host／Origin／路径／大小限制、识别导出／超时和进程组停止。
- `npm run build`：TypeScript 检查和生产构建通过。首次依赖审计发现旧测试工具依赖问题后，将 Vitest 更新到 5.0.4；安装后的在线审计报告零项已知漏洞。
- `npm run test:browser`：Chromium 中五线谱渲染、实际音频输出、暂停、倍速、BPM、按小节跳转、分手控制、MXL／MIDI 导入、MusicXML 下载和窄屏无整页横向溢出均通过。音频检测峰值约 0.16–0.21，验证的是浏览器生成的信号；没有测量外接音箱的声学输出。测试运行时没有外部 HTTP 资源请求。
- `npm run test:pdf`：测试 PDF → 本地 Audiveris → MusicXML → 瀑布与自动播放 → 原 PDF 对照与 BPM 校正均通过。均衡双行的自写测试谱识别出 56 个音符，逐个比较音高、起始拍、时值、谱表均与源 MusicXML 相同。速度标记仍漏识别，默认结果为 120 BPM／16 秒；手动输入原谱 96 BPM 后显示为 20 秒，符合源谱。此测试只覆盖一份自写简单谱，不能推算真实谱集的准确率。
- 早期七小节一行、末尾单独一小节的测试排版，识别只输出 49 个音符，遗漏末尾短行；记录保存在 `test-results/pdf-short-system.json`。最初尝试的 `tessdata_fast` 模型不支持引擎所用 legacy 模式，已换为标准 `tessdata`，最终日志没有该初始化错误。短行和速度识别仍作为已发现限制保留。
- 原始测试记录、截图和 PDF 在 `test-results/`；测试来源事件对照见 `test-results/omr-comparison.json`。文档 README 已验证仅包含规定的两个内容章节。
- 1366 × 768 小笔电视口中，播放按钮位于约第 681 像素，首屏可操作；本地健康查询、许可资源与启动器识别已有服务均已验证。临时服务正在识别 PDF 时发送停止信号，服务正常退出，未留下其创建的 Audiveris 进程。

## 2026-10-14 界面与识别流程调整

删除主界面引导句、宣传标语、固定底栏和英文装饰标题。界面与五线谱改为深色。控制项集中在右侧垂直工具栏，默认隐藏；“工具”或 Tab 呼出，Esc 收起。必要的错误与识别结果记录仍保留在工具栏／状态区域。来源与许可入口移入工具栏。

琴键上边界支持 Pointer Events 拖动与键盘上下方向键调整高度，约束范围为 40–260 像素并保证瀑布区域至少 100 像素。黑键高度按白键高度比例同步调整；浏览器 localStorage 保存高度。点按琴键通过同一个本地采样器发声，黑键优先命中；试听不改变播放位置，不受左右手静音控制，但受总音量控制。

PDF 识别改为两阶段：先用 Audiveris GRID 检测全书五线谱，读取 `.omr` 中具备五条谱线的 staff，随后仅用选中的原页号继续转录。介绍／说明等无谱页不进入转录；同一页上的音乐速度等必要记号仍保留，曲目及作曲家文字不用于瀑布事件。原始 PDF 不修改，对照默认定位到首个被选中的乐谱页。相关引擎参数依据 [官方 CLI 文档](https://audiveris.github.io/audiveris/_pages/guides/advanced/cli/)。页面筛选依赖谱线检测，严重模糊或特殊记谱仍可能误判。

百分比依据已到达的引擎处理阶段及页数计算，属于阶段工作量估计，不是耗时比例或准确率。筛选约占 0–25%，转录占 25–95%，导出为 97%，导出结果准备完成后才显示 100%；失败不会显示完成。两阶段共享原十分钟处理预算。为兼容仍在运行的旧服务，前端在旧接口没有进度字段时从已有日志计算进度。任务状态以原子保存的 `job.json` 持久化；完成任务重启后仍可查询，重启中断的任务明确标记失败。

本次验证：音乐／音频测试 23 项；服务端 14 项测试通过，包括页面选择、纯文字拒绝、阶段进度与任务恢复；合计 37 项自动测试通过。Chromium 验证默认隐藏的垂直工具栏、Tab／Esc、琴键点击发声、边界拖动 90→140 像素及保存、14%→55%→100% 进度显示、原有播放控制和窄屏布局。真实三页 PDF（文字介绍／乐谱／说明）仅识别第 2 页，完整输出 56 个音符；第 1、3 页被跳过；纯文字 PDF 以未检测到五线谱结束。测试记录见 `test-results/page-filter.json`，命令为 `npm run test:pdf-filter`（需要 Chromium 和 pdfunite；生成文件仅用于测试）。

更新期间发现 4280 服务已有用户 PDF 正在处理，因此保留其运行，最新版另在 loopback 4283 提供；没有中断旧任务。旧任务结束后可以停止旧服务并按通常方式在默认 4280 启动新版。

随后前一项旧任务自身达到原服务十分钟识别限时；检查发现默认服务还有另一项任务在运行，因此取消默认端口切换，保留 4280 运行，新版继续在 4283 提供。前一项任务的原 PDF、日志和超时状态仍保留；没有停止正在运行的任务。识别百分比并不代表准确率，长谱仍受十分钟处理预算限制。
